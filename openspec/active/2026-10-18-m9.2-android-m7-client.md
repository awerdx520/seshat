# M9.2 Android 端接入 M7（uid + 增量同步）

## 当前状态

- 阶段：Phase 3（Implement）· **T0 已通过**，T1~T6 待开始
- 已确认：方案 ✅（用户 2026-10-18）——D1 本地索引用 prefs JSON（零依赖）；D2 **先做 A 批（协议 + 索引 + 增量 + 状态 API uid 化 + 阅读器 uid 接入），再做 B 批（文件同步，支撑书架）**；D3 保留 `WebDavClient`（新代码走 REST）；D4 阅读器**有 uid 就同步、无 uid 走纯本地**
- 前置事实：服务端 M7 已完成（`resources`/`changes`/`refs` 三表、`internal/registry/`、`/api/files|changes|resources|resolve|roots|refs`、schema v7、`docs/sync-protocol.md` + ADR 0003/0004），但**代码尚未 commit**（30+ 文件 untracked）
- 下一步：T1（`RestClient` 扩展）→ T2（`ResourceIndex`）→ T3（`SyncEngine`）→ T4（阅读器 uid 接入）→ T5（`SyncManager` 适配）→ T6（验证与文档）
- 复杂度：大（约 10 文件 / 约 1400 行 / 全新同步模型）
- 父计划：`openspec/active/roadmap.md` 的 M9.2（数据源接入）

## 目标

让 Android 端重新与 M7 服务端**兼容**，并具备增量同步能力：

1. **状态 API uid 化**：进度/批注从 `document_id` 迁到 `uid`（否则服务端一律 `400 invalid_uid`）。实测服务端默认只有单根 `notes`（mirror），A 批按单根实现。
2. **M7 只读协议**：`/api/roots`、`/api/resources`、`/api/resolve`、`/api/changes`。
3. **本地资源索引 + 增量游标**：`uid ↔ (root, path)`、`blob`/`size`/`mtime`、墓碑、`dirty`、单一 `cursor`。
4. **同步引擎（拉取侧，A 批只交付可测类）**：`bootstrap()`（`since=0` 循环到 `has_more=false`）与 `pull()`（`since=cursor`）。**A 批不接线**——不在 Application/MainActivity 里调用，也不做后台轮询；触发点与「服务端已配置」守卫留到 B 批（书架打开/应用启动时调用）。
5. **阅读器 uid 接入**：由外部显式传入 uid 时按 uid 读写进度与批注；无 uid（外部 SAF 打开）时保持纯本地。

**B 批（文件同步）不在本计划范围**，另立计划；届时支撑书架（mirror 全量镜像 + ondemand 按需下载）。

可机械判定的验收标准：

1. `cd android && ./gradlew :app:assembleDebug` 成功（L1）。
2. `cd android && ./gradlew :app:testDebugUnitTest` 全绿，用例总数 ≥ 290（既有 260 + 新增 ≥30）（L2）。
3. **T0 前置验证**：本地起 Go 服务端，`curl` 能跑通 `/api/roots`、`/api/changes?since=0`、`/api/resources`（L3，证据为原始响应片段）。
4. 静态断言：`grep -rn "document_id" android/app/src/main/java` 在中 `sync/` 与 `reader/` 下**为 0**（除 KDoc 说明迁移历史外不得有实际调用）。

## 设计

### 0. 客观事实（实现必须遵守）

| 项 | 事实 |
|---|---|
| uid | 26 字符 Crockford Base32 `^[0-9A-HJKMNP-TV-Z]{26}$`；**服务端生成**，客户端不生成；rename 不变；删除后同路径重建复用原 uid |
| resolve | `GET /api/resolve?root=&path=`（另有互斥的 `?doc_id=tag:path` 形态，**A 批不实现**）；错误只有 `400 invalid_argument`（参数组合非法/缺失）与 `404 unknown_uid`（未登记/墓碑）。**resolve 从不返回 `invalid_uid`**（它没有 uid 入参可校验） |
| changes | `since`（seq，缺省 0）/`limit`（≤2000）/`has_more`/`next_cursor`；op ∈ `create/update/rename/delete`；**不含 size/mtime**；`old_path` 仅 rename 有 |
| roots | `{tag, mode∈{mirror,ondemand}, default}` |
| files | （B 批）`GET` 原始字节支持 `Range`/`If-None-Match`→304；`PUT` 原始字节 ≤32 MiB、`If-Match`→412；`DELETE`；`POST /api/resources/{uid}/move` |
| 状态冲突 | body `updated_at` 落后 → `409 conflict` |
| 旧值 | 32 位 hex（epub 内容哈希）与 `uri.toString()`（pdf）**都会被判 invalid_uid** |

### 1. L1 协议层：扩展 `sync/RestClient.kt`

不复用第二套 OkHttp 封装，**扩展现有 `RestClient`**（它已封装 base URL、Bearer、`Json`、`ApiException`）：

- **状态 API uid 化**：`getProgress(uid)` / `setProgress(uid, position, updatedAt?)` / 批注三件套的 `documentId` 参数与 DTO 字段统一改名 `uid`，JSON 字段 `document_id` → `uid`（用 `@SerialName("uid")`，**不要残留 `@SerialName("document_id")`**）。注：`RestClient.setProgress` **现有签名已含 `updatedAt`**；真正缺 `updatedAt` 透传的是 `RestSyncApi.setProgress` / `SyncManager.pushProgress`（**属 T5**，不在 T1）。
- **新增 M7 只读端点**：
```kotlin
fun roots(): List<RootDto>                                // 响应体为 {"roots":[...]}，内部解包
fun resources(root: String? = null, prefix: String? = null, sinceMtime: Long? = null, includeDeleted: Boolean = false, limit: Int = 500): ResourcesPageDto
fun resolve(root: String, path: String): String?          // 404 → null；400 → 抛 ApiException
fun changes(since: Long, limit: Int = 2000): ChangesPageDto
```
- DTO 需注意：`roots` 响应有外层 `RootsResponse(roots: List<RootDto>)` 包装；`seq` / `size` / `mtime` 一律用 **`Long`**（服务端为 int64，用 `Int` 会解码异常）；JSON 全 snake_case，须用 `@SerialName("next_cursor")` / `@SerialName("has_more")` / `@SerialName("old_path")` / `@SerialName("changed_at")` 等。
- DTO（`@Serializable`，均 `ignoreUnknownKeys`）：
  - `RootDto(tag, mode, default)`
  - `ResourceDto(uid, root, path, kind, blob, rev, size, mtime, createdAt, updatedAt, deletedAt)`
  - `ResourcesPageDto(items: List<ResourceDto>, hasMore)`
  - `ChangeDto(seq, uid, op, root, path, oldPath, blob, rev, changedAt)`
  - `ChangesPageDto(changes: List<ChangeDto>, nextCursor: Long, hasMore)`
- 错误分流：`400 invalid_uid` / `404 unknown_uid` 由 `ApiException`（已有 `statusCode` + `code`）承载，调用方按 `code` 分支。

### 2. L2 索引层：新增 `sync/ResourceIndex.kt`

- 存储：`SharedPreferences("seshat_resource_index")`（**普通 prefs，非机密**）+ 单文件 JSON。
- 结构：
```kotlin
@Serializable
data class ResourceEntry(
    val uid: String,
    val root: String,
    val path: String,
    val blob: String = "",
    val size: Long = 0,
    val mtime: Long = 0,
    val deleted: Boolean = false,
    val dirty: Boolean = false,
)
@Serializable
data class ResourceIndexDocument(
    val cursor: Long = 0,
    val entries: List<ResourceEntry> = emptyList(),
)
```
- API（读写函数注入，**纯逻辑可 JVM 测**）：
  - `cursor(): Long` / `setCursor(value: Long)`
  - `all(): List<ResourceEntry>` / `alive(): List<ResourceEntry>`（`deleted=false`）
  - `findByUid(uid): ResourceEntry?` / `findByPath(root, path): ResourceEntry?`
  - `upsert(entry)` / `rename(uid, newPath)` / `markDeleted(uid)` / `clear()`
  - `entriesInRoot(root): List<ResourceEntry>`

### 3. L3 引擎层：新增 `sync/SyncEngine.kt`

- 构造：`SyncEngine(api: SyncApi, index: ResourceIndex)`，其中 `interface SyncApi { fun changes(since: Long, limit: Int): ChangesPageDto }`（便于 fake 测试）。
- `bootstrap(): BootstrapResult`：循环 `changes(since = 0, limit = 2000)` 直到 `hasMore == false`；逐页 `apply(page.changes)`；**先应用事件、再存 `nextCursor`**（崩溃时最多重复处理一页，幂等）。
- `pull(): PullResult`：从 `index.cursor()` 开始同上循环。
- `apply(changes)` 事件语义：
  - `create` / `update` → `upsert(ResourceEntry(uid, root, path, blob, deleted = false))`
  - `rename` → `rename(uid, path)`（`oldPath` 仅用于日志/调试，不做二次匹配）
  - `delete` → `markDeleted(uid)`（**保留 uid 与 path**，供 B 批的墓碑判断与「同路径重建复用 uid」）
- 结果类型：`data class PullResult(val applied: Int, val cursor: Long, val pages: Int)`。
- 并发/失败：`ApiException` 直接向上抛（由调用方决定重试）；`apply` 必须幂等（同 seq 重复应用结果一致）。

### 4. L4 接入层：阅读器 uid

- `EpubReaderActivity` / `PdfReaderActivity` 新增可选 extra `EXTRA_UID`（`String`）：
  - `intentForFile` / `intentForUri` / `intent` 增加可选参数 `uid: String? = null`。
- **键选择的唯一判定点在 Activity 层**（重要，避免五个 Store 各写一套判断）：
  ```kotlin
  // Activity 内唯一一处键选择：有 uid 用 uid，否则沿用旧 documentId
  private val effectiveKey: String = uid ?: documentId
  ```
  随后把 `effectiveKey` **作为 `documentId` 字段值 / `docId` 参数**透传给各 Store（`ReadingProgressStore` / epub `AnnotationStore` / `PdfProgressStore` / `PdfAnnotationStore` / `PdfInkStore`）——**Store 内部零改动**（它们继续按接收到的 key 读写）。
- **同步守卫**（M10.6 不变量）：只有 `uid != null` **且** `SettingsStore.toConfig() != null`（地址+令牌齐备）时才构造 `RestClient` 并同步；任一不满足则完全跳过网络（不抛异常、不提示错误），保持纯本地。
- 本地旧键清理（一次性）：五个 Store 各加 `clearLegacy()`，**全部按「32 位 hex」与「含 `:` 的 uri」两类特征删除**（uid 为 26 位 Base32，既非 32 位 hex 也不含 `:`，不会误删）：
  - `ReadingProgressStore`、epub `AnnotationStore`、`PdfProgressStore`、`PdfAnnotationStore`、`PdfInkStore`（键分别形如 `<id>`、`<id>`、`pdf_progress_<id>`、`pdf_annotations_<id>`、`pdf_ink_<id>`，需剥前缀后判断）。
  - 用 `SharedPreferences` 的 `legacy_cleared` 布尔标记保证只跑一次；并在 tech-debt 记「旧数据不迁移」。

### 5. `sync/SyncManager.kt` 适配

- 其 `documentId` 参数与内部 mapper 的 `docId` 语义统一改名为 `uid`；
- `setProgress` 增加 `updatedAt` 参数（从 `ReadingProgress.updatedAt` / `PdfProgress.updatedAt` 传入），使 409 生效；
- 不新增「首次全量/墓碑/游标」逻辑（那属于 `SyncEngine`）；`SyncManager` 保持「按某个 uid 做一次双向同步」的职责。

## 注意事项

- **T0 是硬前置**：M7 代码未提交且可能有编译问题；T0 失败必须停下来报告，不要在客户端硬编码猜测契约。
- **契约以服务端实现为准**：`changes` 不含 `size`/`mtime`（ondemand 根需额外 `GET /api/resources/{uid}`，B 批处理）；`move` 端点当前只允许默认根（B 批处理）。
- **索引是派生状态**：`ResourceIndex` 可随时 `clear()` 后 `bootstrap()` 重建，不得成为唯一真相。
- **`cursor` 先应用后存**：保证崩溃时最多重复应用一页（幂等），绝不丢事件。
- **墓碑保留 uid 与 path**：服务端「同路径重建复用 uid」依赖此信息。
- **旧键清理只做一次**：用 `SharedPreferences` 的一个 `legacy_cleared` 布尔标记，避免每次启动重扫。
- **索引的容量与并发边界**：`ResourceIndex` 用单个 prefs JSON，按「数千条资源、单文件数百 KB」设计；**A 批假定单线程调用、不加锁**（同步由调用方串行化）；超量时应评估迁移 Room/SQLite（B 批评估）。
- **`cursor` / `since` 一律 `Long`**：服务端为 int64，Kotlin 侧不得用 `Int`（会溢出/解码异常）。
- **零新增依赖**：不引入 Room/SQLite；索引走 prefs JSON。
- **不改 WebDAV**：`WebDavClient` 保持现状，新代码只走 REST。
- **真机验证非本计划必须**（端到端需服务端可达）；但 T0 的 curl 必须完成。若后续要真机验证，需先确认设备已解锁（`mDreamingLockscreen=false` 且 `mCurrentFocus` 不含 `NotificationShade`）。
- **不破坏既有不变量**：M9.1 安全（令牌只经 `putSecret`）、M9.2 存储分层、M9.2/M10.5 渲染管线、M10.6 服务端可选。
- **不得读取** `data/secrets.env` / `android/keystore.properties` / `release.keystore`；本地起服务端时用临时令牌（环境变量注入，不落盘）。
- **起服无 `-config` 参数**：`cmd/server` 硬编码读当前目录的 `config.yaml`，必须 `go build` 到临时目录后在该目录内运行，绝不可在仓库根直接 `go run ./cmd/server`（会写进 `./data/`）。
- **本地请求要绕代理**：本机设有 `http_proxy`，`curl 127.0.0.1` 会被代理截获返回 503（空响应体），造成「服务就绪」的假象；一律加 `--noproxy '*'`，且就绪判定只认 200。
- **A 批按单根实现**：实测默认配置只有 `notes`（mirror）一个根；不要把「多根 / ondemand」写进 A 批逻辑（留 B 批）。
