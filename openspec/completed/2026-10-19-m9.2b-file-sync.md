# M9.2 B 批 文件同步（/api/files 通道 + 接线 SyncEngine + 书架远端数据源）

## 当前状态
- 阶段：Phase 4（Review & Document）· **T1~T9 完成（代码/单测/文档 + 真机 3/3 通过，2026-10-19）**
- 下一步：已归档（2 项复验待设备就绪）
- 已确认：方案 ✅（用户 2026-10-19 确认：会配 ondemand 书库根；接受 BG-A + BG-B 全量交付；新增依赖为零）
- 前置：M9.2 A 批已完成并归档（`openspec/completed/2026-10-18-m9.2-android-m7-client.md`）；A 批的 `ResourceIndex`/`SyncEngine` **当前零调用方**
- 复杂度：大（约 12 文件 / 约 1800 行 / 跨网络-存储-UI 三层）
- 前置事实（探查确认，实现必须遵守）：
  1. `GET /api/files/{path...}?root=` 支持 `Range`（206/416）、`If-None-Match`（304），`ETag` 为内容 git blob sha1（带引号），`Accept-Ranges: bytes`（由 `http.ServeContent` 提供）
  2. `PUT /api/files` 请求体上限 **32 MiB**（`maxFileBytes = 32 << 20`），超限 400 `invalid_argument`；`If-Match`/`If-None-Match` 任一不满足 → 412 `etag_mismatch`；成功返回 `{uid,root,path,blob,etag,rev,seq,created}`
  3. `DELETE /api/files` 为**软删**（写墓碑），路径未登记存活资源 → 404；目录按路径段收集子树
  4. `POST /api/resources/{uid}/move` body `{"to": "根内路径"}`；**只允许默认根（mirror）**，非默认根 → 403 `root_read_only`；目标被占 → 409
  5. `GET /api/resources/{uid}` 返回 `size/mtime/blob/rev` 等全字段
  6. `/api/changes` **不含** `size/mtime` → 新条目 `dirty=true`，需回填
  7. 服务端默认只有单根 `notes`（mirror）；`ondemand` 根需在 `config.yaml` 的 `webdav.roots` 显式声明；`ondemand` 根**不可写**、`blob` 恒空（只能用 `size`/`mtime` 判断）
  8. `ResourceEntry` **无 `rev`**；`ResourceIndex` **无锁**（单线程假定）、无 `dirty` 查询/清除方法
  9. `BookItem.file: File` 是必填 → 远端条目必须落盘才能进书架
  10. `CoverKeys.keyFor(file)` 含 `length` + `lastModified` → 下载后键变，旧封面残留
  11. `RestClient` **无任何 files/move 封装**；`ReaderFragment` **无下拉刷新**（无 swiperefreshlayout 依赖）、无 WorkManager

## 目标
分两段交付，**BG-A 完成后即可单独验收**：

**BG-A（接线与元数据，不碰文件字节）**
1. `ResourceIndex` 线程安全 + 新增 `dirtyEntries(root)` / `clearDirty(uids)` / `upsertAll` 的批量清脏能力
2. `MetadataBackfill`：用 `GET /api/resources?root=X` 分页全量拉取 → 回填 `size/mtime` → 清 `dirty`
3. `SyncCoordinator`：装配 `RestClient` + `ResourceIndex` + `SyncEngine`，提供 `syncNow()`（首次 `bootstrap`、之后 `pull`）与 `roots()` 缓存
4. 书架远端数据源：`BookLibrary` 合并「远端清单条目」（未下载的书显示标题/大小/时间 + 「未下载」标记）
5. 并发保护：同步、回填、书架扫描串行（单一 executor）
6. 刷新触发：书架 `onResume` + 刷新按钮 + 首次进入

**BG-B（文件通道）**
7. `RestClient` 新增：`getFile(root, path, ifNoneMatch, rangeStart)`、`putFile(root, path, bytes, ifMatch, ifNoneMatch)`、`deleteFile(root, path)`、`moveResource(uid, to)`
8. 按需下载：点击「未下载」条目 → 下载到 `filesDir/books/.part` → 校验 → 原子 rename → 打开阅读器；下载失败回退提示
9. 上传：导入的本地书 ≤32 MiB 可上传（`If-None-Match: *` 新建），超限/过大提示不传；上传成功后回填 uid 与元数据
10. `move` 跟随：服务端 rename 事件 → 本地文件重命名 + `ResourceIndex.rename`（已有方法）
11. UI：书架条目区分「本地/远端未下载/下载中」；下载进度用现有 `ProgressBar` 或条目内文本

## 设计

### 0. 共同约束
- **零新增依赖**（不加 swiperefreshlayout、不加 WorkManager、不加协程）；异步统一用 `Executors.newSingleThreadExecutor()`
- 同步逻辑必须**不阻塞主线程**；所有网络调用在后台 executor
- 幂等：`bootstrap`/`pull` 可重复调用；回填可重复调用
- 不破坏既有不变量：M9.1 安全（令牌只经 `putSecret`）、M9.2 分层、M10.6 服务端可选（`SettingsStore.toConfig() == null` 时**零网络**）

### 1. `ResourceIndex`（改造，保持既有 API 兼容）

```kotlin
@Synchronized fun cursor(): Long
@Synchronized fun setCursor(value: Long)
```

- 加锁方式：对**所有** public 方法加 `@Synchronized`（简单可靠；索引操作 O(n)，锁粒度可接受，KDoc 说明）

- 新增方法需测试（`ResourceIndexTest` 追加 ≥6 例：dirtyEntries 过滤墓碑/非目标根、applyMetadata 清 dirty 且保留 deleted、未知 uid 忽略、并发调用不丢条目）

### 2. `sync/MetadataBackfill.kt`（新建，纯逻辑可测部分 + 网络部分）
```kotlin
/**
 * 把 `/api/resources` 的 size/mtime 回填到本地索引的 dirty 条目。
 * 策略：按 root 分页推进（limit 2000，`since` 为 mtime 秒）；对每个能按 uid 命中且 dirty 的条目生成 update，
 * 拉取结束后一次性 applyMetadata。
 */
class MetadataBackfill(
    private val api: ResourcesApi,
    private val index: ResourceIndex,
) {
    fun backfill(root: String): BackfillResult
}
/** 服务端 /api/resources 靠 since(mtime 秒) 推进，响应体无游标。 */
fun interface ResourcesApi {
    fun resources(root: String, sinceMtime: Long?, limit: Int): ResourcesPageDto
}
data class BackfillResult(val updated: Int, val pages: Int)
```
- `ResourcesPageDto` 复用 A 批 `RestClient` 中的定义（`items: List<ResourceDto>` + `@SerialName("has_more") hasMore`），
  其中 `ResourceDto` 已含 `uid/root/path/kind/blob/rev/size/mtime/created_at/updated_at/deleted_at`；
  回填只需 `uid/size/mtime/blob/deletedAt` 五项，B 批不新增 DTO
- 首页 `since = null`；后续页 `since = 本页 items 的 max(mtime)`（服务端语义 `mtime >= since`，故同秒条目会重复返回）
- **同秒边界处理**：若某页 `max(mtime) == 上一页的 since` 且该页没有带来任何新的 `dirty` uid → 视为「本秒已处理完」并把 `since` 加 1 后继续；这样既不死循环也不漏（同秒内的条目在上一页已全部返回）
- **空页即结束**：若某页 `items` 为空（服务端已无更多），直接结束本次回填（不要尝试取 `max(mtime)`）
- **声明**：回填是**尽力而为 + 幂等**——某次运行若因分页边界漏掉少量 `dirty` 条目，它们保持 `dirty=true`，下次 `syncNow()` 自然重试；不得为此抛异常
- 删除「连续两页相同条目集合 → 抛 IllegalStateException」这条安全阀（改为上面的 since+1 推进），保留一个硬上限 `maxPages = 50`（超出则停止并返回已回填数，KDoc 说明）
- 只处理 `deleted == false` 且 `dirty == true` 的条目；服务端已墓碑（`deletedAt` 非空）的条目不回填，改为 `markDeleted`
- 测试（`MetadataBackfillTest` ≥7 例）：单页、多页 since 推进、同秒边界、maxPages 触顶、墓碑转 deleted、未知 uid 忽略、重复调用幂等

> **语义边界**：`/api/resources` 的 `since` 是 mtime 秒级、无游标，同秒多条只能靠「since+1」推进；
> 因此回填保证「最终一致」（下次 sync 重试），**不保证单次全量**。

### 3. `sync/SyncCoordinator.kt`（新建）
```kotlin
/** 同步编排：装配 RestClient + ResourceIndex + SyncEngine，串行执行（单线程 executor）。 */
class SyncCoordinator(
    private val index: ResourceIndex,
    private val restFactory: () -> RestClient?,   // 返回 null 表示未配置服务端 → 全链跳过
    private val backfillFactory: (RestClient) -> MetadataBackfill,
    private val executor: ExecutorService,
) {
    fun syncNow(onDone: (SyncOutcome) -> Unit)     // 首次 bootstrap，之后 pull + backfill
    /** /api/roots 的缓存（含 tag/mode/isDefault 以便上传前判断是否可写）。 */
    fun roots(): List<RootDto>
    /** 使 roots 缓存失效（设置页保存服务端配置后调用）。 */
    fun invalidateRoots()
    /** 服务端配置变更后调用：清 restFactory 缓存 + 调 invalidateRoots()。 */
    fun invalidateConfig()
}
sealed interface SyncOutcome {
    data object NotConfigured : SyncOutcome      // 服务端未配置：零网络，不报错
    data class Ok(val applied: Int, val backfilled: Int, val cursor: Long) : SyncOutcome
    data class Failed(val message: String) : SyncOutcome
}
```
- `RootDto(tag: String, mode: String, isDefault: Boolean = false)`：A 批已在 `RestClient` 中定义并复用（`@SerialName("default")`），B 批直接使用，不重复定义
- `restFactory()` 内部用 `SettingsStore.toConfig()`；返回 null → `NotConfigured`（**不触发任何网络**）
- 首次判断：`index.cursor() == 0L` → `bootstrap()`，否则 `pull()`
- 顺序：sync → backfill（按 `roots()` 逐个根回填）
- 缓存策略：首次 `syncNow()` 时拉取；`invalidateRoots()` 后下次调用重拉
- 上传前用 `roots().firstOrNull { it.tag == targetTag }?.mode == "mirror"` 判断可写，ondemand 根直接拒绝并提示
- `restFactory` 结果缓存：首次调用后持有 `RestClient`；设置页保存服务端配置时调用
  `invalidateConfig()`（清缓存 + 调 `invalidateRoots()`），避免每次 sync 都走 SecurePrefs 解密
- 单线程 executor，`syncNow` 提交任务后立即返回；`onDone` 回到主线程由调用方决定
- 测试（`SyncCoordinatorTest` ≥5 例）：未配置 → NotConfigured 且 restFactory 未被调用、cursor=0 走 bootstrap、cursor>0 走 pull、backfill 在所有根上执行、异常 → Failed

### 4. 书架远端数据源（改造 `BookLibrary` + 新建 `RemoteBookSource`）
```kotlin
/** 远端清单里的书籍候选（尚未落盘）。 */
data class RemoteBook(
    val uid: String,
    val root: String,
    val path: String,
    val name: String,        // path 的文件名部分
    val size: Long,
    val mtime: Long,
)

internal object RemoteBookSource {
    /** 从 ResourceIndex 取某根下扩展名为 epub/pdf 的存活条目。 */
    fun fromIndex(index: ResourceIndex, root: String): List<RemoteBook>
    /** 远端条目是否已落盘（按 path 在 booksDir 下同名文件存在且长度匹配）。 */
    fun localFileOf(booksDir: File, book: RemoteBook): File?
}
```
- `BookItem` 新增字段：`remote: RemoteBook? = null`（null 表示纯本地书）；`file: File` 对远端未下载的书**指向预期落点**（`booksDir/<name>`），并用 `isDownloaded: Boolean` 标记
- `BookItem` 新增 `uid: String? = null`（来自 `RemoteBook.uid`，或本地文件按 `index.findByPath` 反查）
- **阅读器打开时必须传 uid**（这是进度同步闭环的关键）：
  `ReaderFragment.openBook(item)` → `EpubReaderActivity.intentForFile(context, item.file, item.uid)` /
  `PdfReaderActivity.intent(context, Uri.fromFile(item.file), item.uid)`
  （两个工厂的 `uid: String? = null` 参数在 M9.2 A 批已就绪）
- 上传成功后：把返回的 `uid/root/path/size/mtime/blob` 写入 `ResourceIndex`，并**重新扫描书架**使该条目带上 uid
- 下载完成后：从 `RemoteBook.uid` 直接带上（无需反查）
- 若 `uid == null`（纯本地书）→ 阅读器走现有「无 uid 纯本地」路径（M9.2 A 批已实现）
- **远端 `BookItem` 占位字段规则**：

| 字段 | 远端未下载时的取值 |
|---|---|
| title | `RemoteBook.name` 去扩展名 |
| type | 由扩展名判定（epub/pdf） |
| author | null |
| totalCount | 0（`BookShelfLogic.progressPercent` 已对 total<=0 返回 0） |
| progressKey | `RemoteBook.path`（仅作占位；下载完成后重新扫描会替换为真实键） |
| percent | 0 |
| lastReadAt | 0（未读过） |
| importedAt | `RemoteBook.mtime` |
| uid | `RemoteBook.uid` |
| isDownloaded | false |

- **封面**：远端未下载的书无本地文件 → `CoverCache.load` 不可用，adapter 显示占位底色 + 「未下载」文本；
  下载完成并重新扫描后才生成封面
- `BookLibrary.load()` 合并：本地扫描结果 + `RemoteBookSource.fromIndex(index, root)` 中「本地无同名文件」的条目
- 排序/过滤复用 `BookShelfLogic`；过滤「未读」时远端未下载的书按 0% 处理
- 测试（`RemoteBookSourceTest` ≥6 例：只取 epub/pdf、过滤墓碑、`localFileOf` 长度匹配/不匹配、同名冲突、空索引）

### 5. `RestClient` 新增文件通道
```kotlin
fun buildGetFile(root: String, path: String, ifNoneMatch: String? = null, rangeStart: Long? = null): Request
fun buildPutFile(root: String, path: String, bytes: ByteArray, ifMatch: String? = null, ifNoneMatch: String? = null): Request
fun buildDeleteFile(root: String, path: String): Request
fun buildMoveResource(uid: String, to: String): Request

/** 下载到临时文件；304 → null；返回 (file, etag)？ */
fun downloadFile(root: String, path: String, target: File, ifNoneMatch: String? = null): File?
fun uploadFile(root: String, path: String, bytes: ByteArray, ifNoneMatch: String? = null): FileWriteResponse
fun deleteFile(root: String, path: String): FileDeleteResponse
fun moveResource(uid: String, to: String): MoveResponse
```
- `buildGetFile` 的 `root` 用 query 参数 `?root=`；`path` 逐段编码（复用现有 `apiUrl`/`addPathSegment` 思路，但 files 端点路径需按 `/` 分段）
- `rangeStart != null` → `Range: bytes=<start>-`
- `downloadFile`：写入 `<name>.part` 的 `OutputStream` 必须 **close() 之后**才 `renameTo(target)`；
  任何异常路径都要 `delete()` 该 `.part`（`try/catch/finally`）；`renameTo` 失败 → 抛错并删 `.part`
- `304` → 返回 null（不触碰本地文件）
- **前置大小校验**：超限时抛 **`IllegalArgumentException("文件超过 32 MiB 上限：<size>")`**（不伪造 HTTP 状态码）；
  调用方捕获后提示用户（常量 32 MiB 与服务端一致）
- DTO：`FileWriteResponse(uid, root, path, blob, etag, rev, seq, created)`、`FileDeleteResponse(uid, uids, root, path, seq)`、`MoveResponse(uid, root, from, to, seq)`
- 测试（`RestClientTest` 追加 ≥12 例）：构建 URL 与 query、Range 头、If-Match/If-None-Match、304 → null、超限前置拦截（`IllegalArgumentException`）、move body、错误码分流

### 6. 按需下载（改造 `ReaderFragment` + 新建 `reader/BookDownloader.kt`）
```kotlin
class BookDownloader(
    private val restFactory: () -> RestClient?,
    private val booksDir: File,

    /** 下载远端书籍到 booksDir；已存在且长度匹配则直接返回。 */
    fun ensureLocal(book: RemoteBook, onProgress: (Long) -> Unit = {}): DownloadResult

```
- 落点：`booksDir/<name>`（与 `RemoteBookSource.localFileOf` 一致）；下载到 `<name>.part` 后 rename
- 点击书架条目：`isDownloaded` → 直接打开；否则 `ensureLocal` → Ready 打开 / 失败 Toast
- 下载中标记：`BookItem` 的 UI 状态（`Downloading`）——**实现方式**：Fragment 内维护 `downloadingPaths: MutableSet<String>`，adapter 据此显示「下载中…」
- **BG-A 阶段（下载未实现时）**：点击 `isDownloaded == false` 的条目 → Toast「尚未下载（文件同步将在下一段交付）」，不崩溃

### 7. 上传（改造 `ReaderFragment` 的导入回调）
- 导入成功后：若 ≤32 MiB 且服务端已配置 → 后台上传（`If-None-Match: *`）→ 成功回填 `ResourceIndex`（uid/path/size/mtime/blob）→ 刷新书架
- 超限 → Toast「文件超过 32 MiB，暂不支持上传（仅保存在本地）」
- 上传失败 → Toast 提示但**本地文件保留**

### 8. `move` 跟随（改造 `SyncEngine` 或 `SyncCoordinator`）
- `SyncEngine.apply` 的 rename 分支已更新索引 path；B 批需**额外**把本地文件重命名：
  ```kotlin
  // 在 SyncCoordinator 的 pull 完成后
  val renames = /* 本次 pull 中 op=rename 的 (uid, oldPath, newPath) */
  renames.forEach { (uid, oldPath, newPath) ->
      val oldFile = File(booksDir, oldPath.substringAfterLast('/'))
      val newFile = File(booksDir, newPath.substringAfterLast('/'))
      if (oldFile.exists() && !newFile.exists()) oldFile.renameTo(newFile)
  }
  ```
- move 跟随：先 `oldFile.renameTo(newFile)`，失败则跳过并记 `Log.w`（不中断同步）
- **本地扁平存储限制**：`booksDir` 无目录层级，本地文件名 = `path.basename`。
  若服务端 `dirA/foo.pdf` 与 `dirB/foo.pdf` 同时存在，本地只有一个 `foo.pdf`。
  策略：move 跟随为 **best-effort**——仅当「`oldFile` 存在 且 `newFile` 不存在」时重命名；
  否则 `Log.w` 跳过（不覆盖、不删除），并记 tech-debt
- **注意**：`SyncEngine.apply` 目前不返回变更明细 → 需扩展 `SyncResult` 或在 `SyncEngine` 内暴露 `lastRenames`（二选一，报告中说明选择）

### 9. 并发与刷新
- 单一 `syncExecutor`（`SyncCoordinator` 持有）；书架扫描沿用它（或让 Fragment 复用 coordinator 的 executor）
- `ResourceIndex` 加 `@Synchronized` 后，即便扫描与同步在不同线程也安全
- 刷新触发点：`onViewCreated` 首次、`onResume`、刷新按钮、导入成功后、下载完成后

### 10. 配置与文档（用户侧动作）
- **服务端配置**：在 `config.yaml` 的 `webdav.roots` 增加 ondemand 根，示例：
  ```yaml
  webdav:

      - tag: notes
  ```

### 验收口径修正（真机推翻了最初的判据）

1. **书架卡片标题取 EPUB OPF 的 `<dc:title>`，不是文件名。**
   示例书的 OPF 标题是「示例书：笔记系统的阅读器」，因此**不能**按「文件名是否出现」判定书架内容；
   应以「索引里的 uid 是否出现在书架数据集」或「卡片数量/封面」判定。
2. **`move` 跟随的判据是「索引 path 跟随 + 旧路径 404」，不是「本地出现新文件名」。**
   按需下载设计下，**从未打开过的书本来就不落盘**，`files/books/` 里没有它属于正确行为。
3. 设备坐标系：`wm size` 报 2136×3200（竖屏物理值），但 dump/tap 实际使用横屏 3200×2136，自动化脚本需以 `screencap` 尺寸为准。

## 注意事项
- **服务端 roots 是用户侧前置**：未配 `ebooks` 前，`RemoteBookSource` 只会返回 mirror 根内的书；功能应优雅降级（不报错）
- **32 MiB 上限是硬约束**：不得声称支持大文件；超限必须显式提示
- **`ResourceIndex` 加锁后仍假定单进程**（`SharedPreferences` 跨进程不安全，KDoc 说明）
- **`PdfRenderer` 与下载并发**：下载写 `.part` 期间不得让 `PdfBookMetaReader`/`CoverCache` 读到 `.part`（只扫描 `booksDir` 下扩展名文件，`.part` 不匹配）
- **封面旧键残留**：下载换文件 → mtime 变 → 新键；不主动清理旧键（记 tech-debt）
- `DefaultBookMetaReader.read` 目前「非 pdf 一律当 epub」——B 批需加一行断言：扩展名必须是 epub/pdf，
  否则返回 null（防止未来把 `.part` 之类交给它解析）
- **不实现**：>32 MiB 上传（分片）、后台定时同步（WorkManager）、下载断点续传、`rev` 条件更新
- **真机验证需服务端可达**：优先 `adb reverse tcp:8080 tcp:8080` + 客户端地址填 `http://127.0.0.1:8080`
