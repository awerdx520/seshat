## 目标

让 Android 成为批注契约的完整参与方，同时补齐服务端契约缺口：

1. 服务端 `annotations` 能承载「原文 vs 备注」「高亮/笔迹/文本批注」的区分（v8 迁移，纯 ADD COLUMN）。
2. EPUB 的 location 有跨端约定（`chapter:<spineIndex>@<startOffset>-<endOffset>`），EPUB 批注的选中原文不再在同步时丢失。
3. Android 端从「能写不能看」变为「能看/能改/能删」，且手写笔迹进入服务端同步（按 `docs/api.md §4.5.1` 的 ink 协议，一笔一条）。
4. 同步层补齐 update/delete 传播与 409 冲突合并，不再静默吞错。

## 设计

### 数据契约（v8）

迁移第 8 条：`ALTER TABLE annotations ADD COLUMN kind TEXT NOT NULL DEFAULT 'note';` 与 `ALTER TABLE annotations ADD COLUMN selected_text TEXT NOT NULL DEFAULT '';`。
`text` 语义保持不变（备注正文/显示摘要），`kind` 取值 `note` / `highlight` / `ink`，`selected_text` 存选中原文。

三者填充矩阵：

| kind | `text` | `selected_text` |
|---|---|---|
| note | 用户备注正文 | 选中原文（可空串） |
| highlight | 空串 | 选中原文（必非空） |
| ink | 空串 | 空串 |

**text 校验规则（v8 放宽）**：`kind = note` 时 `text` 必填（保持现有契约）；`kind = highlight` / `ink` 时 `text` 必须允许空串。服务端在 `CreateAnnotation` / `UpdateAnnotationAt` 内按 `kind` 分支校验，并同步更新 `docs/api.md` §4.1 与 `docs/errors.md` 中「text 为空 → invalid_argument」的表述。

**幂等（服务端新增，非改键）**：服务端当前无去重，本轮**新增**——`CreateAnnotation` 先按 `(uid, kind, location, text)` 查询既有记录，命中则返回该记录且 HTTP 状态码 `200`（新建仍 `201`）。该去重是 T6「本地已有笔迹一次性补登」幂等的前提。

`ctx`：Emacs 端对 `kind=ink` 的条目显示为「第 n 页手写（N 笔）」，不依赖 `text`。

### location 约定

| 载体 | 形态 |
|---|---|
| PDF 文本批注 | `page:<n>`（1-based，现状保留） |
| PDF 高亮 | `page:<n>;rect:<x0>,<y0>,<x1>,<y1>`（已定稿，本轮不产新） |
| PDF 笔迹 | `page:<n>;ink:<color>,<widthPt>,<x0>,<y0>,...`（一笔一条，坐标 PDF point，原点左上、y 向下、两位小数） |
| EPUB | `chapter:<spineIndex>@<startOffset>-<endOffset>`（0-based spine 序号；offset 为章内字符偏移，半开区间） |

**EPUB location 的承载**：`BookAnnotation` 新增 `location` 字段（缺省空串）承载该串；`chapterIndex` 保留并由 location 派生/回填。`EpubSyncMapper.location()` 取 `annotation.location.ifBlank { "chapter-${chapterIndex}" }`，`fromRemote` 解析 `chapter:<spineIndex>@<start>-<end>` 回填 `chapterIndex` 与 `location`；旧记录（location 为空）行为与现状完全一致。fromRemote 须兼容两种形态：含 `@` 的按新格式解析（回填 `chapterIndex` 与 offsets），不含 `@` 的沿用 `chapterIndexOf` 旧逻辑（`chapter-<n>`），保证服务端存量 EPUB 批注拉取后 `chapterIndex` 不归零。

### 同步语义

- 409（进度）：重拉 → 以 `updated_at` 较新者为准 → 本地更新则带新 `updated_at` 重发一次。
- 409（批注）：重拉 → 服务端版本为准，本地改动记录为冲突提示（不静默丢弃）。
- 删除：本地删 → `DELETE /api/annotations/{id}` → 本地移除；离线时把 `serverId` 加入 `pendingDeletes` 待重试（不复用 `dirty`）。
- 幂等：键为 `(kind, location, text)`（服务端为 `(uid, kind, location, text)`，客户端与 Emacs 队列同构）；ink 的 location 天然唯一。
- flush 时机（修订）：**不接 `SyncCoordinator`**（它无 `pull()` 且与 `SyncManager` 零耦合）。改为 ① 阅读器 `onStop`；② 阅读器内 `pullAnnotations` 成功返回后立即 flush 一次。
- 本地 id 语义（修订）：两个 `fromRemote` 把 `remote.id` 写入 `serverId`，本地 `id` 由 store 生成（`AnnotationStore.add` 补 UUID；`PdfAnnotationStore.add` **改为** `id <= 0` 时生成 `nextId`，与其既有 `nextId()` 对齐），**不承接服务端 id**；`pullAnnotations` 合并时先按 `serverId` 匹配本地记录（命中则更新，未命中才新增），避免每次拉取重复入库。
- push 回填闭环（修订）：`createAnnotation` / `updateAnnotation` 成功后，把返回的服务端 `id` 写入本地记录 `serverId`（`updateAnnotation` 同时用返回的 `updated_at` 刷新本地 `updatedAt`），并清 `dirty`。`pullAnnotations` 的匹配顺序：① 先按 `serverId` 命中则 update（回填 `serverId`、清 `dirty`）；② 未命中再按 `(kind, location, text)` 兜底去重，兜底命中则 update 并回填 `serverId`；③ 仍未命中才 `add`。

## 注意事项

- `internal/storage/state_v7_test.go` 有**两处**硬编码 7（`:125`、`:252`），加 v8 必须同步改，否则 L1 直接失败。
- 服务端 `text` 校验按 kind 放宽后，`docs/api.md` §4.1 的「`uid`、`location`、`text` 均必填」必须同步改成按 kind 表述，否则文档与实现不一致（列入 T8 验收）。
- 服务端 `annotations` 的 `location` 视为**不透明串**，不得据其内容做分类/查询（分类只能靠 `kind`）。
- 一笔一条 annotation：列表 UI 必须按 `kind` 分组并把 `ink` 默认折叠，避免淹没文本批注。
- PDF 文本选区层（`rect:` 采集/真高亮）**不在本轮**，必须写入 tech-debt，不得顺手开工。
- Android 无 instrumentation 测试目录：EPUB 偏移采集与抽屉交互只能抽纯函数单测 + 手工验收，计划里不得声称自动化覆盖。
- 不新增第三方依赖（零新增依赖是本仓库既定纪律，pdfbox-android 为用户授权的唯一例外）。
- Emacs 端改动必须向后兼容：老批注缺 `kind`/`selected_text` 时行为与改动前完全一致。
- 每次 commit 使用简体中文提交信息。
- 服务端不对 `kind` 做枚举校验；取值约定 `note` / `highlight` / `ink` 只写进 `docs/api.md` §4 字段表，客户端只发这三个值。若将来改为校验，必须同步 `docs/errors.md` 与 `api.md` 错误码表。（注意区分：`text` 按 kind 分支的校验属于本轮已实施内容，见 T1 与 `docs/errors.md` 变更域；`kind` 本身的枚举校验本轮仍不做。）text 校验口径：仅 `kind == "note"` 时必填，其余值（含未知/空 `kind`）一律放行空 `text`；`kind` 缺省填充在 storage 层 `CreateAnnotation` 内兜底（`if kind == "" { kind = "note" }`），API 层缺省仅作文档说明——Go 结构体字段反序列化后为空串，显式 INSERT 时 SQL 的 `DEFAULT 'note'` 不生效。
- `ink` 的 location 由点序列决定，理论上两笔「完全相同的点序列」会碰撞 `(kind, location, text)` 被去重；与 `decisions.md` 2026-10-16「同位置同文本有意重复不敏感」同源，属已知可接受限制，不在本轮修。
